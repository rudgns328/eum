## 1. 시스템 개요

### 1.1 아키텍처

```
┌─────────────────────────────────────────────┐
│                 프론트엔드                    │
│   대시보드 · 업로드 · 실행계획 · 알림설정      │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│                  API 서버                     │
├─────────────────────────────────────────────┤

│   · 상태 관리                                 │
├─────────────────────────────────────────────┤
│  [확률론 영역 — LLM]                          │

       │                      │
┌──────▼────────┐    ┌────────▼──────────┐
│   규정 DB      │    │   사용자 상태 DB   │
│  (정적 JSON)   │    │   (케이스 단위)    │
└───────────────┘    └───────────────────┘
```

### 1.2 설계 원칙

1. **결정론과 확률론을 코드 레벨에서 분리한다.** 기한·상속분은 LLM을 거치지 않는다.
2. **실시간 외부 의존성을 만들지 않는다.** 크롤링·마이데이터 연동 없음.
3. **부분 실패를 허용한다.** LLM 파싱 실패 시 수동 입력 폴백.
4. **모든 안내에 출처를 붙인다.** 기관명 + 확인일자 필수.

### 1.3 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 프론트엔드 | Next.js + Tailwind | 배포 간편, SSR |
| 백엔드 | Next.js API Routes (App Router, 확정) | CLAUDE.md 스택 준수 |
| DB | Supabase (확정) | Vercel 서버리스에서 SQLite는 영속성 없음 — CLAUDE.md 스택 준수 |
| LLM | Claude API (Vision 지원) | 문서 파싱 필수 요건 |
| 벡터 검색 | 불필요 (규정 DB가 소규모 구조화 데이터) | 전문 검색 대신 필드 필터링 |
| 배포 | Vercel | 9/7~9/11 접속 가능 URL 필요 |
| 알림 | 이메일 (Resend 등) | 알림톡은 사업자 등록 필요로 제외 |

**주의:** 규정 DB는 수십 건 규모의 구조화 JSON이므로 벡터 DB가 불필요합니다. 조건 필터링으로 후보를 좁힌 뒤 LLM에 전달하는 방식이 정확도·비용 모두 우수합니다.

## 2. 데이터 모델

### 2.1 규정 DB — 기관별 절차 규정

**정본은 `data/rules/*.json` 7개 파일입니다** (standard.json + 기관 델타 6종). 수집·검증 경위와 필드별 근거는 `docs/04_규정데이터_수집결과.md`에 있으며, 04 문서 6장의 스키마 변경 요구사항이 본 절과 실데이터에 반영되어 있습니다.

**스키마 핵심 필드** (04 §6.1~6.2)

| 필드 | 값/형태 | 비고 |
|---|---|---|
| `verification` | `{level, source_confirmed_at, call_verified_at, call_target, note}` | level: `unverified` \| `source_confirmed` \| `call_verified` |
| `simplification_type` | `consent_relaxation` \| `submission_channel` | 은행·증권은 동의 완화, 보험은 접수 채널 — 축이 다름 |
| `amount_basis` | `principal` \| `valuation` \| `claim_amount` | 증권은 평가액(`valuation_date_basis: application_date`), 보험은 청구금액 |
| `simplification_rules[]` | `max_amount, required_heirs, min_total_heirs, consent_ratio, consent_type, consent_basis, effect` | `consent_type: physical_visit`(신한)은 위임장 대체 불가. `consent_basis`가 null이면 충족 여부 단정 금지 → "확인 중" |
| `required_documents[].condition` | 04 §6.4 enum | `unless_simplified`는 상속인 측 서류에만 적용. `target: "피상속인"` 서류는 소액이어도 면제되지 않음 |
| `processing_days` | `{simplified, standard_min, standard_max, unit}` | 소액/일반 분기 |
| `min_visiting_heirs` | 정수 | 비대면 위임장이 있어도 최소 내점 인원 존재 |
| `discrepancies[]` / `call_log[]` | 배열 | 안내문 vs 실무 불일치 기록 / 통화 원문 Q&A (재검증 근거) |
| `unresolved_fields[]` | 배열 | UI "확인 중" 배지 트리거. 기관별 하드코딩 금지 |

업권별 확장: 보험은 `beneficiary_rule`(수익자 지정 여부가 서류 전체를 가르는 분기)·`prescription`(소멸시효 3년), 증권은 `securities_handling`(예탁금/증권 분리, 출고 시 계좌 개설 필요) — 상세는 04 §6.2와 각 JSON 참조.

**예시 (kb_bank.json 발췌)**

```json
{
  "institution_id": "kb_bank",
  "verification": { "level": "call_verified", "source_confirmed_at": "2026-08-14", "call_verified_at": "2026-08-21" },
  "simplification_type": "consent_relaxation",
  "amount_basis": "principal",
  "simplification_rules": [
    { "max_amount": 3000000, "required_heirs": 1, "effect": "미내점 상속인의 위임장·인감증명서 제출 면제" },
    { "max_amount": 10000000, "min_total_heirs": 3, "consent_ratio": 0.5, "consent_basis": "headcount" }
  ],
  "processing_days": { "simplified": 0, "standard_min": 2, "standard_max": 5, "unit": "business_days" },
  "min_visiting_heirs": 1
}
```

## 3. 모듈 명세

### 3.1 기한 엔진 (규칙)

**입력:** 사망일, 조회 신청일(선택), 부동산 보유 여부
**출력:** 기한 목록 + D-day + 심각도

```
calculate_deadlines(death_date, options) -> Deadline[]
```

**처리 로직**
1. 각 기한 규정의 base 필드에 따라 기준일 산출
   - `death_date` — 사망일 그대로
   - `death_date_month_end` — 사망일이 속한 달의 말일
2. offset_months 가산
3. 오늘 기준 D-day 계산
4. applies_if 조건 평가 후 미해당 항목 제외
5. renunciation은 사용자가 인지일(상속개시를 안 날)을 별도 입력하면 그 날짜 기준으로 재계산
6. 영업일 계산은 `data/holidays.json`(2026~2027, 노동절·제헌절 신규 공휴일 반영) 기준. 파일을 직접 생성·수정하지 않는다
7. 기한 말일이 토요일·공휴일인 경우 — 민법 제161조상 기간은 익일로 만료하나, MVP는 보수적으로 당초 날짜를 기한으로 표시한다(실제보다 늦은 날짜를 안내하는 위험 회피)

**시간 함정 감지**
```
if 조회_미신청 and D-day(renunciation) < 30영업일:
    경고: "조회 결과는 20영업일 소요.
          지금 신청해도 D-{n}에 결과가 나옵니다."
```

시간 함정 8건(`data/deadlines.json > time_traps`)은 전부 결정론 조건이므로 Phase 1~2에서 규칙으로 구현합니다. 3.4의 1단계 필터는 이 구현을 재사용합니다.

**주의:** LLM을 절대 경유하지 않습니다. 순수 날짜 연산입니다.

### 3.2 법정상속분 엔진 (규칙)

**입력:** 상속인 구성
**출력:** 각 상속인의 법정상속분

**민법 규칙**
- 1순위: 직계비속 + 배우자
- 2순위: 직계존속 + 배우자 (직계비속 부존재 시)
- 3순위: 형제자매 (배우자·직계 부존재 시)
- 4순위: 4촌 이내 방계혈족 — MVP 계산 범위 외. 감지 시 "전문가 확인 필요"만 출력
- 배우자는 동순위 상속인의 **1.5배**
- 대습상속: 상속인이 될 자가 먼저 사망한 경우 그 직계비속이 대신 상속

**예시**
```
배우자 1 + 자녀 2
→ 1.5 : 1 : 1 = 3/7 : 2/7 : 2/7
```

**주의:** 이는 민법 조문의 기계적 적용이며 법률 조언이 아닙니다. "누가 얼마를 받는 것이 유리한가"는 다루지 않습니다.

### 3.3 문서 파싱 모듈 (LLM Vision)

**입력:** 이미지 또는 PDF
**출력:** 구조화 JSON

**대상 문서별 스키마**

가족관계증명서:
```json
{
  "decedent": {"name": "", "death_recorded": true},
  "relations": [
    {"relation": "배우자", "name": "", "alive": true, "is_minor": false},
    {"relation": "자녀", "name": "", "alive": true, "is_minor": false}
  ],
  "confidence": 0.0
}
```

안심상속 / 금융거래 조회 결과:
```json
{
  "institutions": [
    {"name": "", "category": "은행|보험|증권|카드",
     "kind": "재산|빚|null",
     "status": "예금 있음|가입 사실 있음|대출 있음",
     "amount": null}
  ]
}
```

**`kind` — 재산과 빚을 가른다 (2026-09-06 추가).** 조회 결과에는 금융채권만이
아니라 금융채무도 함께 나온다. 금감원 조회는 「금융채권·금융채무·보관금품의
존재유무」를, 안심상속은 대출·보증·카드 미결제까지 알려 준다. 이것을 가르지
않으면 빚이 재산으로 들어가 소액 간소화 판정이 어긋나고, 부채 합계가 0이 되어
`debt_exceeds_asset` 판정이 성립하지 않는다.

문서 표기로만 정하고 읽어서 정하지 못하면 null이다. null인 줄은 결정론 규칙
(`looksLikeDebt` — 대출·채무·카드론·마이너스·연체·보증·미결제)이 대신 본다.
둘 중 하나라도 빚이라 하면 빚으로 둔다 — 빚을 재산으로 넣으면 판단이 불가능해지고,
반대로 넣으면 사용자가 화면에서 바로 알아본다.

**폴백 설계 (필수)**
- confidence < 0.8 → 사용자 확인 화면 표시
- 파싱 실패 → 수동 입력 폼 제공
- **LLM 실패가 서비스 중단으로 이어지지 않아야 합니다**

**프롬프트 원칙**
- JSON 스키마를 명시하고 그 외 출력 금지
- 불확실한 필드는 null로 반환하도록 지시
- 추측 금지를 명시적으로 지시
- 주민등록번호·생년월일은 추출·반환하지 않는다. 미성년 여부(만 19세 미만)만 `is_minor`(boolean)로 판정해 반환 (절대규칙 4)

### 3.4 누락 탐지 엔진 (규칙 필터 + LLM)

**핵심 모듈입니다.** 2단계로 구성합니다.

**1단계 — 규칙 필터 (결정론)**

사용자 상태를 조건으로 규정 DB를 필터링해 후보를 좁힙니다.

```
if 예금액 <= 3000000 and 기관.간소화규칙 존재:
    → "1인 단독 청구 가능" 후보 생성

if 보험.status == "가입 사실만 확인":
    → "담보 확인 필요" 후보 생성

if 부채합계 > 재산합계:
    → "한정승인 검토 + 전문가" 후보 생성

if 자동차 보유:
    → "이전등록 별도 기한" 후보 생성
```

1단계 필터의 시간 함정 판정은 Phase 1~2 구현분을 재사용합니다. `consent_basis`가 null인 간소화 규칙(카카오뱅크 500만 구간)은 충족 여부를 단정하지 않고 "확인 중"으로 처리합니다.

**2단계 — LLM 문맥 판단**

필터링된 후보를 사용자 상황과 함께 LLM에 전달해 관련성을 재평가하고 안내문을 생성합니다.

**출력 형식 (고정)**
```json
{
  "alerts": [
    {
      "severity": "critical|warning|info",
      "title": "",
      "body": "",
      "deadline_ref": "renunciation",
      "requires_expert": true,
      "source": {"institution": "KB국민은행", "verified_at": "2026-08-13"}
    }
  ]
}
```

**법적 안전장치 (하드코딩)**

`requires_expert: true`인 항목은 템플릿이 강제됩니다.

```
"{상황}이 확인됩니다. {제도명} 검토가 필요할 수 있습니다.
 결정 기한 D-{n}. 이 판단은 법률 전문가 상담이 필요합니다."
```

관련 기한이 없는 항목(예: `special_representative_required`)은 "결정 기한 D-{n}." 문장을 생략합니다.

**LLM이 이 문구를 벗어나 판단을 서술하지 못하도록 후처리 검증을 둡니다.** 금지 표현 목록(예: "하셔야 합니다", "유리합니다", "권장합니다")을 필터링합니다.

### 3.5 실행 계획 생성

**입력:** 케이스 상태 + 규정 DB
**출력:** 기관별 액션 카드 + 통합 서류 목록

**처리**
1. 각 기관별로 필요 서류 산출 (표준 규정 + 기관 델타)
2. 간소화 규칙 적용 여부 판정 → 전원 방문 필요 여부 결정
3. 비대면 가능 채널 표시
4. **서류 합산** — 전 기관 필요 서류를 종류별로 집계
5. 방문 순서 제안 (기한 임박순 + 서류 의존성 고려)

**서류 합산 예시 출력**
```
주민센터에서 한 번에 발급받으세요
· 가족관계증명서 6통 (KB 2, 하나 2, 삼성생명 2)
· 기본증명서 4통
· 인감증명서 각 상속인 3통씩
※ 발급일로부터 3개월 이내 원본만 유효
```

## 8. 테스트 시나리오 설계

### 8.1 시나리오 구성 (최소 30건)

| 축 | 변형 |
|---|---|
| 상속인 구성 | 배우자+자녀2 / 배우자만 / 자녀만 / 대습상속 / 형제자매 |
| 재산 규모 | 300만 이하 / 300만~1000만 / 1000만 초과 |
| 부채 | 없음 / 재산 미만 / 재산 초과 |
| 기관 수 | 1곳 / 3곳 / 6곳 이상 |
| 자산 종류 | 예금만 / 예금+보험 / 예금+보험+증권+자동차 |
| 시점 | 사망 직후 / 2개월 경과 / 3개월 임박 |

### 8.2 정답 리스트 사전 작성

각 시나리오별로 "반드시 나와야 하는 알림"을 사람이 먼저 정의합니다.

예시:
```
시나리오 #12
조건: 예금 240만원(KB), 상속인 3명, 부채 없음
정답 알림:
  ✓ KB 300만원 이하 → 1인 단독 청구 가능
  ✓ 전원 방문 불필요
  ✓ D-day 표시
오답으로 처리:
  ✗ 전원 인감증명서 요구 (간소화 규칙 미적용)
```

### 8.3 측정

- **재현율** = 탐지된 정답 항목 / 전체 정답 항목 → **목표 85% 이상**
- **오탐율** = 잘못 제시한 항목 / 전체 제시 항목 → 목표 15% 이하
- **파싱 정확도** = 상속인 구성 정확 추출 / 전체 → 목표 90% 이상

**이 숫자 한 줄이 "LLM 래퍼"라는 인상을 지웁니다. 3주차를 반드시 여기에 쓰십시오.**
